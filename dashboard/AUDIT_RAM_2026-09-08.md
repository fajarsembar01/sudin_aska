# Audit RAM dashboard.app — 8 September 2026

Server menurut pengguna: RAM 4 GB; crash sering terlihat saat membuka User Dashboard atau PANBERSS. Entry point yang diperiksa adalah `dashboard/app.py`.

Audit mencakup route, query, template, pengolahan media, ekspor, dan runtime bersama pada Pengaturan/User Dashboard, PANBERSS, Laporan, Buku Tamu, Monev BOS/BOP, Adiwiyata, Hospitality, Call Center, Supporter, CMS, serta ASKA Insight. Ini pemindaian kode dan pengujian sintetis terisolasi, bukan pengujian seluruh endpoint dengan database produksi.

**Kesimpulan:** ada beberapa alur dengan alokasi RAM yang tumbuh mengikuti seluruh data, serta pemrosesan foto yang mengalokasikan ratusan MiB untuk satu gambar. User Dashboard termasuk kandidat yang sesuai gejala dan sudah direproduksi alokasi memorinya. Belum ada bukti untuk menyatakan satu endpoint tertentu sebagai penyebab OOM produksi.

## Temuan yang paling sesuai gejala

### 1. User Dashboard — seluruh akun dirender, JSON akun berulang (prioritas tinggi)

- Endpoint `/pengaturan/users` memakai handler bersama di [user_management.py:375](user_management.py#L375).
- [queries.py:1821](queries.py#L1821) mengambil semua akun, tanpa `LIMIT`/pagination SQL; `fetchall()` lalu mengonversi hasil menjadi dictionary pada baris 1863–1864.
- [manage_users.html:307](portal/templates/portal/admin/manage_users.html#L307) merender semua akun non-pending; pending juga dirender pada baris 445. Pencarian/filter dilakukan di browser.
- Data lengkap akun disisipkan sebagai JSON pada klik baris, tombol WhatsApp, dan tombol edit (baris 308, 360, 365). Daftar pilihan merge juga dibuat untuk seluruh akun terkait. Akibatnya HTML dan buffer sementara Jinja jauh lebih besar daripada data akun saja.
- **Uji aktual template dengan akun buatan:** 1.000 akun menghasilkan HTML 6,34 MiB dan tambahan peak RSS 57,66 MiB; 5.000 akun menghasilkan HTML 31,50 MiB dan tambahan peak RSS 272,27 MiB.
- Ini dapat menekan RAM server saat request bersamaan; HTML besar juga membebani browser. Belum diketahui jumlah akun produksi atau RAM yang tersedia sebelum request.

**Perbaikan:** pagination dan pencarian SQL, misalnya 25–50 akun per halaman; kirim ID pada tombol, ambil detail ketika dibuka; satu representasi JSON per akun yang sedang ditampilkan; pencarian akun merge melalui endpoint terbatas.

- `/portal/admin/drafts`, [portal/routes.py:5407](portal/routes.py#L5407), mengambil seluruh draft yang cocok lalu seluruh input skor/catatan sebelum merender halaman.
- [portal/queries.py:3475](portal/queries.py#L3475) tidak memiliki pagination; `get_draft_assessment_inputs()` pada baris 3575 mengumpulkan input untuk semua ID. Foto di sini berupa agregat jumlah, bukan byte gambar.
- Route membentuk cache ruangan per sekolah dan menganalisis setiap draft (baris 5417–5450). Filter status hasil analisis baru diterapkan sesudah semuanya diproses (baris 5454).
- [draft_analysis.html:492](portal/templates/portal/admin/draft_analysis.html#L492) juga menyiapkan HTML daftar modal tersembunyi untuk semua/kategori draft, di samping tampilan daftar.
- Pemilihan periode default memakai semua periode: [portal/routes.py:4799](portal/routes.py#L4799).

**Perbaikan:** default periode aktif, pagination sebelum mengambil detail, agregasi status draft di SQL, muat detail/modal saat dibuka. Jangan memuat skor semua draft hanya untuk menampilkan satu halaman.

### 3. PANBERSS — halaman statistik memproses seluruh periode secara default (prioritas menengah)

- Admin yang membuka `/portal/` diarahkan ke statistik: [portal/routes.py:1893](portal/routes.py#L1893).
- `/portal/admin/stats` memanggil banyak query agregasi/daftar dalam satu request: [portal/routes.py:5245](portal/routes.py#L5245). Tanpa filter tahun/periode, helper mengembalikan filter kosong pada baris 4799–4800.
- Histogram sembilan kategori justru mengambil setiap nilai penilaian melalui `fetchall()`, lalu menghitung kategori di Python: [portal/queries.py:2866](portal/queries.py#L2866).
- Galeri statistik melakukan `DISTINCT ON` dan dua subquery skor per kandidat foto sebelum `ORDER BY RANDOM() LIMIT`: [portal/queries.py:1266](portal/queries.py#L1266). Ini kandidat biaya database, perlu pemeriksaan query plan terhadap volume produksi.
- **Batas yang sudah ada:** penilaian terbaru 50, aktivitas staff 100, foto statistik 24, ranking masing-masing 10. Jangan menyimpulkan seluruh foto didekode di RAM Flask ketika statistik dibuka.

**Perbaikan:** periode aktif sebagai default, histogram memakai agregasi SQL, gabungkan/cache ringkasan dengan masa berlaku pendek, periksa indeks dan query plan galeri. Ukur RAM PostgreSQL terpisah dari worker Flask sebelum menyatakan query ini penyebab OOM.

## Temuan besar pada modul lain

### 4. Foto Buku Tamu/Tindak Lanjut dan thumbnail (prioritas tinggi)

- [photo_stamp.py:67](photo_stamp.py#L67) mendekode foto ukuran penuh lalu membuat beberapa buffer RGB/RGBA, overlay, dan hasil komposit; tidak ada pembatasan dimensi atau pengecilan sebelum stamping.
- Terjangkau dari upload transaksi Buku Tamu ([daftar_tamu/routes.py:7519](daftar_tamu/routes.py#L7519)) serta foto tindak lanjut PANBERSS ([portal/routes.py:2255](portal/routes.py#L2255)).
- Batas request default 50 MB pada [__init__.py:58](__init__.py#L58) membatasi byte terkompresi, bukan RAM setelah decode.
- Thumbnail Buku Tamu di [daftar_tamu/routes.py:1703](daftar_tamu/routes.py#L1703) membuka dan menyalin original sebelum mengecilkan. Ada ETag/cache browser, tetapi tidak ditemukan cache hasil thumbnail di disk server; client baru dapat memicu pengolahan ulang.
- Riwayat memakai URL thumbnail secara otomatis; default empat item dan chunk maksimal 20. Beberapa request foto bisa berjalan bersamaan sesuai konfigurasi server.
- **Uji sintetis foto 4000×3000, JPEG 188.629 byte:** stamping menambah peak RSS **226,42 MiB**; pemrosesan thumbnail menambah **90,51 MiB**.

**Perbaikan:** validasi piksel sebelum decode, resize sebelum komposit, overlay hanya area stempel, cache thumbnail di disk atau buat saat upload, batasi jumlah pekerjaan foto bersamaan. Menurunkan ukuran JPEG output saja tidak mengatasi alokasi decode.

### 5. Performa Admin — pagination baru setelah seluruh log dimuat (prioritas tinggi)

- `/overview/admin-performance` dan endpoint detail admin memanggil `fetch_admin_activity_events()` tanpa filter atau limit SQL: [queries.py:4746](queries.py#L4746), [queries.py:4950](queries.py#L4950).
- Sebelas query sumber log dinormalisasi, digabung, dan diurutkan di Python. Filter tanggal/admin serta pagination baru diterapkan sesudahnya. Limit tampilan 400 atau delapan baris tidak membatasi input RAM.
- **Uji fungsi aktual dengan cursor buatan:** 10.000 event menambah peak RSS 23,7 MiB; 50.000 event menambah 119,4 MiB, walaupun respons hanya delapan baris.

**Perbaikan:** filter, agregasi, pengurutan, dan pagination di SQL; query ringkasan terpisah dari query detail; jangan membaca semua sumber semua periode untuk setiap klik halaman.

### 6. Laporan — daftar sekolah menjalankan sinkronisasi global (prioritas tinggi)

- Membuka daftar atau riwayat Laporan sekolah memanggil `sync_no_submissions()` untuk setiap form: [laporan/routes.py:2182](laporan/routes.py#L2182), [laporan/routes.py:2592](laporan/routes.py#L2592).
- Fungsi membaca seluruh riwayat satu form, membangun lookup, lalu daftar INSERT sekolah × periode yang belum terisi: [laporan/routes.py:705](laporan/routes.py#L705).
- Ada batas backfill 90 hari untuk pembentukan periode, tetapi pembacaan riwayat tidak dibatasi 90 hari. Banyak pengguna mengulang pekerjaan global yang sama.
- Request bersamaan juga berpotensi membuat `no_submission` duplikat karena membaca kondisi lama lalu INSERT tanpa upsert/penguncian; unique index pada [schema.py:2072](schema.py#L2072) hanya berlaku untuk status `submitted` dan repeat key non-null.

**Perbaikan:** job terjadwal/idempoten dengan penguncian dan batch terbatas; halaman GET hanya membaca hasil. Tentukan constraint sesuai kebijakan form sebelum membersihkan kemungkinan duplikat.

### 7. Jawaban Laporan dan ekspor Excel (prioritas tinggi)

- [laporan/routes.py:3428](laporan/routes.py#L3428) mengambil seluruh submissions sebelum filter periode; baris 3452 mengambil detail semua submissions terpilih. Accordion tertutup tetap dirender lengkap, tanpa pagination.
- [laporan/queries.py:1161](laporan/queries.py#L1161) memakai `Workbook()` biasa, kemudian `BytesIO` pada baris 1282. Detail setiap submission dibaca dua kali untuk isi dan ringkasan (baris 1176, 1251).
- Detail juga membuat query file per jawaban: [laporan/queries.py:747](laporan/queries.py#L747). Ini memperpanjang waktu request sambil workbook tetap di RAM.
- **Uji export aktual dengan DB buatan:** 10.000 submissions × 20 pertanyaan menghasilkan XLSX 1,14 MiB, tambahan peak RSS **152,11 MiB**, dan waktu 21,19 detik tanpa latensi DB. Dengan 20 jawaban per submission, pola dua kali pembacaan detail dapat memerlukan sekitar 440.000 query detail.
- Ekspor Buku Tamu juga menggabungkan semua halaman kunjungan dalam list, menyalinnya menjadi baris Excel, lalu memakai workbook biasa: [daftar_tamu/routes.py:3313](daftar_tamu/routes.py#L3313), helper baris 1643. CSV memakai buffer penuh juga.

**Perbaikan:** pagination jawaban dan detail sesuai permintaan; filter periode di SQL; batch answers/files; XLSX write-only ke temporary file; CSV streaming dengan cursor server atau batch yang tidak ditumpuk; batasi ekspor bersamaan dan rentang/jumlah data.

### 8. AI/knowledge di worker dashboard dapat menaikkan RAM dasar (prioritas tinggi bila dipakai)

- Call Center mode AI mengimpor pemroses AI ke proses dashboard: [call_center/routes.py:468](call_center/routes.py#L468), pemanggilan saat inbound pada baris 877.
- Refresh knowledge mengimpor handler web dan Telegram: [routes.py:361](routes.py#L361). Handler Telegram langsung membangun chain pada [../handlers.py:50](../handlers.py#L50); refresh web membangun chain lain pada [../web_aska/handlers.py:149](../web_aska/handlers.py#L149). Dua chain dapat tertahan dalam worker yang sama jika kedua jalur berhasil.
- Session AI disimpan dalam dictionary global tanpa eviction jumlah pengguna/TTL: [../web_aska/handlers.py:96](../web_aska/handlers.py#L96), baris 212. Ini pertumbuhan retensi lintas request, berbeda dari buffer sementara halaman.
- Ukuran vectorstore lokal hanya sekitar 3,36 MB; jangan menganggap index lokal sendiri pasti menghabiskan gigabyte. Backend embedding/model dan konfigurasi produksi menentukan tambahan RAM sebenarnya.
- Penghapusan akun bridge pada [call_center/routes.py:2090](call_center/routes.py#L2090) hanya menghapus record DB; tidak menghentikan proses bridge yang sebelumnya dijalankan. Jika bridge masih aktif, proses terkait dapat terus memakai RAM server.

**Perbaikan:** jalankan AI/embedding di service terpisah dengan batas concurrency; reload pada pemilik model; tambahkan TTL/batas session; hentikan dan verifikasi proses bridge sebelum menghapus konfigurasinya.

### 9. Riwayat Buku Tamu SSE dapat menghabiskan slot layanan (prioritas menengah; bukan bukti kebocoran RAM)

- [daftar_tamu/routes.py:6416](daftar_tamu/routes.py#L6416) menahan request sekitar 55 detik dan memeriksa DB setiap empat detik. Snapshot dibatasi 40 baris, sehingga ini terutama masalah concurrency/thread.
- Contoh deployment repo menggunakan dua worker `gthread` tanpa `--threads`: [README.md:85](README.md#L85). Jika benar-benar digunakan tanpa override, default thread adalah satu per worker menurut [dokumentasi Gunicorn](https://gunicorn.org/reference/settings/). Dua stream dapat memenuhi dua slot pemrosesan dan membuat halaman lain terlihat macet.
- Konfigurasi service produksi belum diperiksa. Menambah worker/thread tanpa perhitungan memori dapat memperbesar jumlah pekerjaan foto/ekspor berat yang berjalan sekaligus.

**Perbaikan:** alokasikan layanan SSE yang sesuai atau gunakan polling ringan dengan interval terkontrol; tentukan kapasitas berdasarkan RAM terukur dan request berat. Bedakan timeout/antrean dari OOM.

## Pelaksanaan tahap 1 — User Dashboard

Setelah pengguna menyetujui tahap pertama, kode User Dashboard diubah menjadi pagination SQL maksimal 50 akun per halaman/tab, pencarian dan filter SQL, detail edit/preview melalui request berdasarkan ID, serta pencarian merge maksimal 20 hasil. Tombol WhatsApp hanya menyertakan data kontak yang diperlukan. Riwayat aktivitas dimuat ketika tab History dibuka. Konfigurasi server dan modul PANBERSS belum diubah.

Perbandingan sintetis dengan interpreter dan fixture yang sama, total 5.000 akun:

| Metrik | Sebelum | Sesudah |
|---|---:|---:|
| Akun dirender per request | 5.000 | 50 |
| HTML | 31,498 MiB | 0,277 MiB |
| Tambahan peak RSS render | 271,75 MiB | 2,56 MiB |

Metode tetap template aktual dengan base minimal, data buatan, tanpa database produksi atau layout penuh; angka ini bukan jaminan RSS produksi. Pengujian Python mencakup pagination/filter/count, izin akses detail, pencarian merge, create/edit/verifikasi/reset/merge, dan larangan mutasi dalam preview. Uji Chromium dengan respons simulasi memverifikasi pengambilan detail, pencarian merge akun di luar halaman, submit pencarian server, serta pilih 50 akun pending; tidak ditemukan error JavaScript.

### Pelaksanaan lanjutan — Preview Akun

`/dashboard/pengaturan/preview-akun` sebelumnya memanggil `list_dashboard_users()` dan memfilter seluruh akun di Python. Pemilihan target dan aksi pin juga mengulang jalur seluruh akun. Jalur ini kini memakai pencarian dan pagination SQL maksimal 50 target yang approved dan belum digabung. Akun pin diurutkan lebih dahulu dalam hasil, sedangkan validasi mulai preview/pin mengambil tepat satu ID akun. Target preview aktif tetap dipertahankan ketika target berada di halaman pencarian/pagination lain.

Uji render sintetis dengan total 5.000 akun membandingkan template sebelum dan sesudah: HTML turun dari 6,109 MiB menjadi 0,087 MiB; tambahan peak RSS render turun dari 12,81 MiB menjadi 0,23 MiB. Angka ini hanya mencakup template Preview Akun dengan data buatan dan helper minimal.

### Pelaksanaan tahap 2 — Cek Draft PANBERSS

`/dashboard/portal/admin/drafts` sebelumnya mengambil seluruh draft beserta semua skor, agregat foto, dan catatan dalam satu request. Hasil analisis lengkap lalu disimpan di list Python dan dirender lagi ke empat sumber modal tersembunyi. Jalur ini kini membaca maksimal 100 draft per batch, langsung mengakumulasi ringkasan status/staff, dan hanya mempertahankan 25 draft untuk halaman yang diminta. Hitungan status tetap mencakup seluruh hasil filter. Kartu ringkasan membuka filter server sehingga sumber modal berulang dan JavaScript penyalin HTML dihapus.

Saat halaman dibuka tanpa pilihan periode, periode aktif (atau periode terbaru jika tidak ada yang aktif) dipilih otomatis. Pengguna masih dapat memilih “Semua Tahun” secara eksplisit. Ini mengurangi pekerjaan awal yang sebelumnya mencakup semua periode.

Render sintetis 5.000 draft dengan template lama menghasilkan HTML 35,970 MiB. Template baru yang menampilkan 25 draft menghasilkan 0,139 MiB, turun 99,61%. Pengukuran ini menggunakan base template minimal dan data buatan; beban database serta layout produksi tidak termasuk. Pengujian mencakup batas query 200, pemrosesan batch 100/100/30, pagination setelah filter status, ringkasan inkremental, dan regresi User Dashboard/Preview Akun.

### Pelaksanaan tahap 3 — Performa Admin

Halaman dipindahkan ke `/dashboard/pengaturan/admin-performance` dan kini memakai bulan kalender berjalan sebagai cakupan awal berdasarkan tanggal Jakarta. Filter menyediakan tiga pilihan: bulan tertentu, satu tahun tertentu, dan seluruh riwayat. Rentang terpilih juga diteruskan ke endpoint modal detail admin. URL lama `/overview/admin-performance` mengalihkan pengguna beserta query filternya ke lokasi baru.

Sebelumnya `start` dan `end` baru diterapkan setelah seluruh event dari 11 sumber selesai diambil. Sekarang setiap query sumber mendapat kondisi timestamp `>= awal` dan `< hari setelah akhir` sebelum `fetchall()`. Dengan demikian pembukaan default hanya memasukkan event bulan terpilih ke RAM. Pilihan “Seluruhnya” tetap lebih berat karena memang meminta semua riwayat dan harus digunakan ketika diperlukan.

Performa Admin juga menyediakan PDF bukti kerja sesuai cakupan waktu dan filter fitur yang aktif. Bagian pertama PDF selalu berupa leaderboard seluruh admin yang memiliki minimal satu aksi; admin bernilai nol tidak dimasukkan dan parameter pilihan satu admin dari layar sengaja diabaikan. Bagian berikutnya selalu merekap akun admin yang sedang login dan mengunduh dokumen, bukan akun yang dipilih lewat query. Event periode terpilih diambil satu kali lalu dipakai bersama untuk kedua rekap agar ekspor tidak menggandakan pembacaan log ke RAM.
